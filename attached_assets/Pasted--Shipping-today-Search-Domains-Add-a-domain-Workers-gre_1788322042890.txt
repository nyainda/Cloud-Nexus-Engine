What counts as a "row write"
Every INSERT, UPDATE, and DELETE counts as 1 row write per row affected. The free limit is 100,000/day (resets at midnight UTC).

What's driving your write volume
I inspected your database. Here's what I found:

1. FTS triggers on products — the biggest multiplier
You have 3 triggers on the products table that sync data to a full-text search index (products_fts):

Operation	Row writes per product
INSERT a product	2 (1 product + 1 FTS insert)
UPDATE a product	3 (1 product + 1 FTS delete + 1 FTS insert)
DELETE a product	2 (1 product + 1 FTS delete)
With 5,806 products, a single full product re-sync costs ~17,000 row writes. Do that a few times a day and you've blown through 100K.

2. Write-heavy transaction pattern
Each sale likely writes to multiple tables:

sales (1 write)
sale_items — 1 write per item
inventory_movements — 1+ write per item
audit_log — 1 write
notifications — 1+ write
A single sale with 5 items = ~15–20 row writes. At that rate, ~5,000 sales/day hits the limit.

3. High-volume tables
Table	Rows
notifications	6,782
products	5,806
inventory_movements	6,167
sale_items	3,875
price_history	2,041
sales	1,876
These tables are growing — every new row is a write.

How to stay on the free plan
Quick wins (do these first)
Drop the FTS triggers if you don't need full-text search — this alone cuts product writes by 2–3×:
DROP TRIGGER products_fts_insert;
DROP TRIGGER products_fts_update;
DROP TRIGGER products_fts_delete;
If you need search, use LIKE queries with your existing indexes instead, or rebuild FTS less frequently.
Stop bulk product re-syncs — if your app re-uploads all products on every deploy or sync, change it to only update products that actually changed. Each unnecessary UPDATE costs 3 row writes.
Reduce notification writes — don't create a notification for every minor event. Batch them or only create notifications for important actions.
Skip audit_log for low-importance actions — 74 rows is small now, but if it grows with every API call, it adds up.
Medium-term optimizations
Batch writes — instead of updating products one by one, batch multiple updates into a single transaction. D1 counts rows written, not statements, so this won't reduce the count directly — but it helps you identify and eliminate unnecessary writes.
Cache read-heavy data in KV — if some data doesn't need to be in D1 (like product catalogs that rarely change), store it in Workers KV instead (free tier: 100K reads/day, 1K writes/day).
Move price_history to append-only with cleanup — run a daily cleanup job to delete old price history rows (but note: deletes also count as writes).
If you genuinely need this write volume
If your app truly needs >100K writes/day after optimization, the Workers Paid plan is $5/month and includes 50 million row writes/month (vs. 100K/day free). For an active multi-shop inventory system, that's likely the right path.

Where to check your daily usage
You can monitor row writes in the dashboard:

Go to Workers & Pages → D1
Select greenlink-db
View Metrics → Row Metrics
This shows your daily row reads and writes so you can see exactly when you're approaching the limit.
