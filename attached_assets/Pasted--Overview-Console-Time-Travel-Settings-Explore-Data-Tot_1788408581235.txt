What counts as a "row write"
Every INSERT, UPDATE, and DELETE counts as 1 row write per row affected. The free limit is 100,000/day (resets at midnight UTC).

What's driving your write volume
I inspected your database. Here's what I found:

1. FTS triggers on products — the biggest multiplier
You have 3 triggers on the products table that sync data to a full-text search index (products_fts):

Operation	Row writes per product
INSERT a product	2 (1 product + 1 FTS insert)
UPDATE a product	3 (1 product + 1 FTS delete + 1 FTS insert)
DELETE a product	2 (1 product + 1 FTS delete)
With 5,806 products, a single full product re-sync costs ~17,000 row writes. Do that a few times a day and you've blown through 100K.

Found the problem — your app is running database migrations (DDL statements) on every single request, not just once at deploy time. This is what's burning through your D1 limits.

The evidence
Look at these queries from your analytics — these should run once but are running hundreds of times:

Query	Executions	Problem
ALTER TABLE scan_sessions ADD COLUMN r2_key	232×	Should run once
ALTER TABLE scan_sessions ADD COLUMN archived_at	120×	Should run once
CREATE VIRTUAL TABLE products_fts USING fts5(...)	75×	Should run once
DROP TABLE IF EXISTS products_fts	107×	Should run once
CREATE INDEX idx_audit_shop_date	357×	Should run once
CREATE INDEX idx_sale_items_sale	(cut off, likely 100s)	Should run once
Every time your Worker handles a request, it's re-running all these schema changes. This is catastrophic for your limits because:

Write impact (the 100K/day limit)
Each CREATE VIRTUAL TABLE products_fts rebuilds the full-text search index for all 5,806 products. That's ~5,800+ row writes per execution. At 75 executions = ~435,000 row writes just from FTS rebuilds alone. That's 4× your daily limit.

Each DROP TABLE products_fts also counts as writes. Each ALTER TABLE and CREATE INDEX counts as writes too.

Read impact (the 5M/day limit)
Your top query is also a problem:

SELECT ..., count(*) over () FROM "products" 
WHERE shop_id = ? AND is_active = ? LIMIT ?
708 executions, 3.85M rows read — 57% of all your queries
The count(*) over () window function forces SQLite to scan every matching row before applying the LIMIT, even though you only need a page of results
Combined with the second products query (845K rows), you're at ~4.7M row reads — dangerously close to the 5M/day limit
How to fix it
Fix 1: Stop running migrations on every request (critical)
Your app is running schema setup/migrations inside the Worker request handler instead of once at deploy time. You need to move all DDL statements (ALTER TABLE, CREATE TABLE, CREATE INDEX, CREATE VIRTUAL TABLE, DROP TABLE) out of the request path.

If you're using a migration framework (like Drizzle, Kysely, or a custom migrations table), make sure:

Migrations run once during deployment, not on every request
Your app_migrations table tracks which migrations have already run
The migration check is a quick SELECT against app_migrations, not re-executing DDL
If you're running raw DDL in your Worker code, remove it and run it manually once via the D1 console or wrangler d1 execute:

npx wrangler d1 execute greenlink-db --remote --command "ALTER TABLE scan_sessions ADD COLUMN r2_key TEXT"
npx wrangler d1 execute greenlink-db --remote --command "ALTER TABLE scan_sessions ADD COLUMN archived_at TEXT"
npx wrangler d1 execute greenlink-db --remote --command "CREATE INDEX IF NOT EXISTS idx_audit_shop_date ON audit_log(shop_id, created_at)"
npx wrangler d1 execute greenlink-db --remote --command "CREATE INDEX IF NOT EXISTS idx_sale_items_sale ON sale_items(sale_id)"
Then delete the DDL from your Worker code so it never runs again on a request.

Fix 2: Decide on FTS — create it once or drop it entirely
Your app is caught in a loop of creating and dropping products_fts (75 creates, 107 drops). Pick one:

Option A — Keep FTS (run once):

npx wrangler d1 execute greenlink-db --remote --command "CREATE VIRTUAL TABLE IF NOT EXISTS products_fts USING fts5(id UNINDEXED, shop_id UNINDEXED, normalized_name, canonical_name, sku, category, content='products', content_rowid='rowid')"
Then remove the CREATE VIRTUAL TABLE and DROP TABLE from your Worker code.

Option B — Drop FTS entirely (saves the most writes):

npx wrangler d1 execute greenlink-db --remote --command "DROP TRIGGER IF EXISTS products_fts_insert"
npx wrangler d1 execute greenlink-db --remote --command "DROP TRIGGER IF EXISTS products_fts_update"
npx wrangler d1 execute greenlink-db --remote --command "DROP TRIGGER IF EXISTS products_fts_delete"
npx wrangler d1 execute greenlink-db --remote --command "DROP TABLE IF EXISTS products_fts"
Then remove all FTS-related code from your Worker. Use LIKE queries for search instead.

Fix 3: Remove count(*) over () from product queries
Replace:

SELECT ..., count(*) over () FROM products WHERE shop_id = ? AND is_active = ? LIMIT ?

-- Get the page of results
SELECT id, shop_id, canonical_name, ... FROM products
