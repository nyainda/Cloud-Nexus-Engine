## 1. PRODUCT VISION

GreenLink POS is designed for small and medium agrovet businesses that need:
- Accurate stock
- Instant profit visibility
- Debt tracking
- Intelligent inventory automation

Without complicated accounting software.

**The system is designed around REAL shop behavior:**
```
Staff forget things
Internet fails
Books are still used
Handwriting is messy
Receipts get lost
Products are repeated
Quantities may be missing
Customers buy in bulk
```

The software must adapt to humans — not force humans to become perfect.

## 2. CORE PHILOSOPHY

### The Original Problem (Why This Exists)
```
BROKEN CURRENT FLOW:
Customer buys item →
Cashier sells it (POS or book) →
Item still shows in stock (wrong) →
End of day: staff manually remove items →
Tiresome + staff forget items →
Stock count wrong →
Profit = unknown 😭

THE FIX:
Customer buys item →
Cashier records sale in PWA (5 seconds) →
Stock AUTO reduces immediately →
Profit AUTO calculated instantly →
End of day: owner opens app →
Full profit report already ready →
Zero manual work. Ever. 🎉

FORGOT TO RECORD? (manual removal):
Go to Today's Sales →
Find the item →
Remove it →
System recalculates profit automatically
Even at midnight. Even next day.
```

### Design Philosophy
```
Forgiving software.
Messy human input should still work.

The system must:
  ✅ tolerate shorthand writing        e.g. "BASA" → Basagran 1L
  ✅ tolerate OCR mistakes             e.g. "KNGA" → KINGA
  ✅ tolerate duplicate products       merge, don't break
  ✅ tolerate missing quantities       infer from price
  ✅ support offline workflows         IndexedDB queue
  ✅ support both modern and           POS + book scan
     traditional shop workflows
```

### Final Product Positioning
```
This is NOT just a POS system.

This is:
  Retail Operations OS for Agrovets

Designed around real African retail workflows including:
  notebooks              → OCR scanner recovers missed sales
  handwritten sales      → quantity inference engine
  WhatsApp invoices      → invoice scanner
  offline workflows      → IndexedDB + background sync
  messy inventory        → normalization pipeline
  bulk scanning          → multi-page OCR
  shorthand writing      → alias system
  duplicate pages        → image hash + content detection
  real-world shop chaos  → forgiving matching engine

The system must feel:
  smart
  forgiving
  fast
  practical
  human

While maintaining:
  accurate stock
  accurate profit
  accurate reports
  accurate inventory history
```

## 5. OFFLINE-FIRST STRATEGY

### The Problem
```
Internet is unreliable in many agrovet environments.
Sales cannot stop because WiFi dropped.
```

### The Solution
```
Sales are stored in IndexedDB FIRST.
UI confirms immediately.
Supabase sync happens in background.

Flow:
  Cashier records sale →
  Saved to IndexedDB instantly (< 50ms) →
  "Sale recorded ✅" shown immediately →
  Background worker uploads to Supabase →
  Sync indicator: 🟢 synced / 🟡 pending

Failed Sync Handling:
  If upload fails →
  Sale marked "⏳ Pending Sync" in log →
  After 30 minutes still unsynced →
  Owner notification fires:
    "⚠️ 3 sales not synced — check connection"
  Retry button available
  Never lost — always in IndexedDB
```

### Performance Goals
```
POS search result:    < 100ms
Sale completion:      < 2 seconds
Offline mode:         functional 24+ hours
Low-end Android:      Tecno, Infinix, low RAM devices

Optimizations:
  image compression before OCR upload
  lazy loading for product lists
  virtualized lists (handles 2,610+ products)
  OCR processing in Web Workers (no UI freeze)
  reduced animations on weak devices (detected via navigator)
```

## 6. ROLE PERMISSIONS

```
OWNER
  ✅ View all reports
  ✅ View profit margins
  ✅ Edit prices
  ✅ Override discounts (PIN confirm)
  ✅ Delete products (soft delete)
  ✅ Export data (CSV)
  ✅ Manage PINs
  ✅ Import products (Excel + OCR)
  ✅ Manage suppliers
  ✅ View full audit trail
  ✅ View cash reconciliation
  ✅ Access OCR scanner
  ✅ View inventory movements

CASHIER
  ✅ Record sales
  ✅ Search stock
  ✅ Record debts
  ✅ View debt list (their shop)
  ❌ Cannot see profit margins
  ❌ Cannot see buy prices
  ❌ Cannot edit prices
  ❌ Cannot delete products
  ❌ Cannot export data
  ❌ Cannot see audit trail
  ❌ Cannot access reports
  ❌ Cannot override discounts (needs owner PIN)
```

### PIN System
```
4-digit PIN per role
Stored hashed in Supabase (bcrypt)
Change anytime in Settings (owner only)

Login flow:
  Select shop → select role → enter PIN
  Wrong PIN: shake animation
  3 wrong attempts: 30 second lockout

Owner PIN override (in-session):
  Certain actions require owner PIN even mid-session
  e.g. discount override, price edit, product delete
  Re-enter PIN → action allowed → logged in audit
```

-- ─────────────────────────────────────────────

-- WHY TWO NAME FIELDS:
--   canonical_name  → "Basagran 1L"  shown in POS, receipts, reports
--   normalized_name → "basagran1l"   used for OCR match, fuzzy, duplicates

-- ─────────────────────────────────────────────
-- PRODUCT ALIASES (OCR + shorthand matching)
-- ─────────────────────────────────────────────
product_aliases (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id      uuid REFERENCES products ON DELETE CASCADE,
  alias           text NOT NULL,      -- "BASA", "DAP50", "U50"
  confidence      decimal(4,3),       -- 0.000 to 1.000

  created_at      timestamptz DEFAULT now()

-- Examples:
--   "BASA"   → Basagran 1L       confidence 0.95  auto_generated true
--   "DAP50"  → DAP 50KG          confidence 0.98  auto_generated true

--   "KINGA"  → Kingcode 1L       confidence 0.88  auto_generated true
--   "TINGA"  → Tinga Top 500ml   confidence 0.96  auto_generated true

-- ─────────────────────────────────────────────

-- ─────────────────────────────────────────────
-- INVENTORY MOVEMENTS ← SOURCE OF TRUTH
-- ─────────────────────────────────────────────
inventory_movements (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id     uuid REFERENCES products ON DELETE CASCADE,
  movement_type  text NOT NULL,

  -- RESTOCK      owner added new stock

  -- LOSS         plant died, item damaged, expired

  reference_id   uuid,              -- sale_id | invoice_id | null
  created_by     text,              -- 'owner' | cashier name | 'system'
  created_at     timestamptz DEFAULT now()
)

-- EVERY stock change MUST create a movement record.
-- This table is the complete history of all inventory activity.
-- Used for: stock audits, discrepancy detection, reports

sale_items (

## 9. DATA NORMALIZATION PIPELINE

### Why This Is Critical
```
Good OCR and search systems are mostly:
  good preprocessing
  + clean data
  + smart matching

NOT magical AI.

If DB contains:
  Basagran 1litre
  Basagran 1 litre
  BASAGRAN 1L
  Basa 1L

→ OCR matching breaks
→ fuzzy search returns duplicates
→ reports show 4 products instead of 1
→ stock split across phantom duplicates

After normalization:
  canonical_name:  "Basagran 1L"
  normalized_name: "basagran1l"
  tokens:          ["basagran","basa","1l","basagran1l","basa1l"]

→ everything matches cleanly
→ OCR finds it instantly
→ one product, one stock count
→ clean reports
```

### The Full Pipeline
```
Excel Upload
    ↓
Step 1: Parser
  Extract 8 of 37 columns:
  NAME, SKU, PURCHASE PRICE, SELLING PRICE,
  PROFIT MARGIN, UNIT, ALERT QUANTITY, MANAGE STOCK
    ↓
Step 2: Cleaner
  Fix all messy data (see rules below)
    ↓
Step 3: Normalizer
  Generate canonical_name, normalized_name, tokens
    ↓
Step 4: Validation
  Flag missing prices, negative stock, missing SKU
    ↓
Step 5: Duplicate Detection
  Compare normalized_names — 85%+ similarity = flag
    ↓
Step 6: Preview Screen
  Human reviews everything before DB write
    ↓
Step 7: Save to Supabase
  Only confirmed, clean records written
```

### Step 2: Cleaning Rules

**Trim whitespace:**
```
"  BASAGRAN 1L  " → "BASAGRAN 1L"
```

**Normalize units:**
```
1litre / 1 litre / 1ltr / 1lt / 1Litre  → 1L
500ml / 500 ml / 500ML                   → 500ml
250gm / 250 gram / 250GM                 → 250g
20lt / 20ltr / 20LT                      → 20L
50kg / 50KG / 50 kg                      → 50kg
```

**Standardize case:**
```
bAsAgRaN               → Basagran
ELGON 20LT PUMP        → Elgon 20L Pump
rid out 1lt            → Rid Out 1L
POULTRY MICROBES 500ML → Poultry Microbes 500ml
```

**Auto-assign categories by keyword:**
```
"pump","sprinkler","drip","pipe","valve",
"filter","hose","nozzle","emitter","cam lock",
"dripline","lay flat","riser"             → Irrigation

"basagran","rid out","glyphosate",
"paraquat","atrazine","weedicide"         → Herbicide

"tinga","mancozeb","ridomil","score",
"bravo","copper","milraz","dithane"       → Fungicide

"kingcode","karate","lambda",
"cypermethrin","emamectin"                → Insecticide

"dap","urea","npk","can ","foliar",
"optimizer","calcium","boron","humic"     → Fertilizer

"seed","maize","tomato","bean",

### Purpose
```

### OCR Technology Stack
```
Image Processing:  OpenCV.js     (browser, free)
OCR Engine:        Tesseract.js  (browser, free)
                   OR Gemini Vision (subscription, better handwriting)
Product Matching:  Fuse.js       (fuzzy, free)
Image Storage:     Supabase Storage (free tier)
Processing:        Web Workers   (no UI freeze)

Gemini Vision advantage:
  Handles messy handwriting dramatically better
  Understands context (can infer product from partial name)
  Worth subscribing for handwritten notebook scans

Architecture: try Gemini first, fall back to Tesseract.js
```

### Document Preprocessing (before OCR)
```
Camera image →
  Step 1: Auto document detection
          Detect paper edges in frame
          Show overlay guide: "Align paper to corners"
  Step 2: Crop to paper boundary
  Step 3: Perspective correction (flatten if angled)
  Step 4: Shadow removal
  Step 5: Contrast enhancement
  Step 6: Text sharpening
  Step 7: Convert to high-contrast grayscale
→ THEN OCR runs

Goal: fix poor lighting, angle, shadows
      before OCR attempts to read anything.
Accuracy difference: 40% raw → 85%+ preprocessed.
```

### Full OCR Pipeline
```
Take Photo
    ↓
Document Detection + Preprocessing (OpenCV.js)
    ↓
OCR Extraction (Tesseract.js or Gemini Vision)
    ↓
Line-by-line Parsing
  Split on newlines
  Each line = potential product entry
  Handle: "DAP 2800", "BASA ×3", "UREA 50KG 2pcs"
    ↓
Product Matching Engine
  For each parsed line:
  1. Check tokens index
  2. Check product_aliases
  3. Fuzzy match normalized_names (Fuse.js)
  4. Category inference from keywords
  → Assign confidence score
    ↓
Quantity Inference Engine
  If no qty found: try price ÷ known sell price
    ↓
Duplicate Detection
  Image hash check (same scan uploaded twice?)
  Content similarity check (overlapping pages?)
    ↓
Repeated Product Merging
  Same product appears multiple times →
  Sum quantities before review screen
    ↓
Review Screen (ALWAYS — never skip)
    ↓
Human Confirms / Edits
    ↓
Apply to Inventory
  Creates inventory_movements (OCR_IMPORT)
  Updates stock_qty
  Logs to audit_trail
```

### Quantity Inference Engine
```
Problem: Cashier writes total amount instead of quantity.

  8400 ÷ 2800 = 3 (exact)

Handles multiple patterns:
  "DAP 2800"   → 2800 ÷ 2800 = 1  → DAP × 1
  "DAP 5600"   → 5600 ÷ 2800 = 2  → DAP × 2

## 11. CORE BUSINESS LOGIC

### 11.1 The Core Sale Flow
```

5. System executes in one transaction:

   g. Checks stock_qty vs alert_qty → fires notification if needed

## 12. INVENTORY MOVEMENT ENGINE

```
inventory_movements is the source of truth.

Every single stock change — regardless of source — 
creates a movement record.

Movement types:

SALE
  Source: POS cashier sale
  qty_change: negative
  reference_id: sale_id

RESTOCK
  Source: owner adds new stock
  qty_change: positive
  reference_id: null (or invoice_id if from scan)

OCR_IMPORT
  Source: notebook or invoice scan confirmed
  qty_change: negative (for sales recovery)
              or positive (for invoice restock)
  reference_id: invoice_id or scan_session_id

LOSS
  Source: plant died, item damaged, expired
  qty_change: negative
  reference_id: plant_loss_id or null

ADJUSTMENT
  Source: manual correction by owner
          or sale removal by staff
  qty_change: positive or negative
  reference_id: sale_id being reversed

RETURN
  Source: customer returned item
  qty_change: positive
  reference_id: original sale_id

Every movement records:
  before_qty: stock BEFORE change
  after_qty:  stock AFTER change
  created_by: who did it
  created_at: exact timestamp

This enables:
  Complete stock audit at any time
  Discrepancy investigation
  Inventory reports by movement type
  Prove exactly when/why stock changed
```

## 17. PLANTS MODULE 🌱

```
Completely separate module from main stock.
Own navigation item.
Own CRUD, own stock logic.

Why plants are different:
  Sold individually (not by pack)
  Can die/get damaged without a sale (losses)
  Size/age variants matter to price
  Seasonal availability (can toggle off-season)
  Loss tracking important for profitability

Plant size variants:
  Seedling | Small | Medium | Large | Mature

Recording a sale (same as POS):
  Select plant → qty → SELL/DEBT
  Stock reduces → profit calculated

Recording a loss (no sale):
  Select plant → how many died → reason:
    drought / pest / overwatering / transplant shock / other
  → stock reduces
  → inventory_movement created (LOSS)
  → NOT counted as sale or revenue
  → Shows in loss report: "10 Bougainvillea lost — drought"

Loss report:
  Total plants lost (period)
  Cost of losses (purchase price × qty lost)
  Loss by reason (drought / pest / etc.)
  Most loss-prone plants
```
