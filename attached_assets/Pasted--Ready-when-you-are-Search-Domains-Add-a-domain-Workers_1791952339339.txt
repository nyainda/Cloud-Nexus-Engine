Why you're burning through 5M rows/day
D1 bills by rows scanned, not rows returned. The most common cause is queries that do full table scans on unindexed columns. For example, if you have a table with 10,000 rows and a query like SELECT * FROM orders WHERE user_id = ? with no index on user_id, that single query reads all 10,000 rows — even if it only returns 5. A few hundred requests like that per day = millions of rows read.

I wasn't able to query your database directly (the query API needs elevated permissions I don't have), but here's how to find and fix the problem:

Step 1: Check your metrics in the dashboard
Go to your D1 database metrics page to see the rows_read trend: → D1 Metrics

Step 2: Find the expensive queries
Open the D1 console and run these to see your schema and identify missing indexes: → D1 Console

-- List all tables
SELECT name FROM sqlite_master WHERE type='table';

-- List all indexes (to see what's already indexed)
SELECT name, tbl_name FROM sqlite_master WHERE type='index';

-- For each table, check row counts
SELECT 'your_table_name' AS table_name, COUNT(*) AS row_count FROM your_table_name;
Then for every query your Worker runs, use EXPLAIN QUERY PLAN to check if it's doing a full SCAN (bad) or SEARCH ... USING INDEX (good):

EXPLAIN QUERY PLAN SELECT * FROM your_table WHERE some_column = ?;
If you see SCAN your_table, that query is reading every row — add an index:

CREATE INDEX idx_yourtable_somecolumn ON your_table(some_column);
For multi-column WHERE clauses, use a composite index:

CREATE INDEX idx_yourtable_col1_col2 ON your_table(col1, col2);
Step 3: Common patterns to fix
Pattern	Problem	Fix
WHERE col = ? with no index	Full table scan	CREATE INDEX on that column
WHERE a = ? AND b = ? with single-column index	Scans all matching a rows, then filters	Composite index on (a, b)
JOIN t2 ON t2.x = t1.y where t2.x unindexed	Repeated scans of joined table	Index the join column
SELECT * FROM table (no WHERE)	Reads entire table every time	Add a WHERE clause + index, or cache the result
Step 4: Other quick wins
Cache read-heavy query results in your KV namespace (SESSIONS) — if the same data is requested repeatedly, serve it from KV instead of re-querying D1
Use LIMIT on queries that don't need all rows
Avoid SELECT * when you only need specific columns (doesn't reduce row reads, but reduces data transfer)
Check for loops in your Worker code that might be running the same query multiple times per request
